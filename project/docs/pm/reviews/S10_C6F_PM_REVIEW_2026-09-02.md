### F1 — P1: multiple same-generation wrong-key claimants are classified as “missing”; replay creates a third job

**Code:**

- `app/api/routes/s10_full_apply.py:197-293`
- `app/api/routes/s10_full_apply.py:987-1052`
- `tests/test_s10_full_apply_api.py:2189-2226`

The new `_s10_wrong_identity_claimant` scans by expected workspace/generation,
but returns a claimant only when `len(rows) == 1`. Zero rows, multiple rows and
query failure all return `None`. The replay path interprets `None` as a true
orphan and calls `_s10_repair_missing_submit_job`. This directly contradicts
C6F §5.3 item 3 (multiple/ambiguous rows fail closed) and §5.7's required
single durable-job resolution path.

Codex reproduced the omitted case through the real route and JobService on
fresh SQLite:

1. Submit returned 202 and created one job.
2. Its key was changed to `tampered-a-*`.
3. A second queued job with the same workspace, run generation and manifest but
   key `tampered-b-*` was created.
4. Identical replay returned **200 `reused=true`** and inserted canonical key
   `s10_full_apply_job:<run-id>`.

Actual count changed **2 -> 3**. Expected is 409/422 with both wrong claimants
unchanged and count 2. The existing C6F test covers only exactly one wrong-key
row, so it cannot expose the `len(rows) > 1 -> None` branch. A combined
key/workspace/type tamper and candidate-query error are also not fail-closed.

**Required correction:** replace the split key lookup plus one-row special case
with one candidate resolver that classifies exact, wrong, ambiguous/multiple
and true-zero cases from independent durable identities. Any wrong/ambiguous
candidate or read error must block repair. Add all-row tests for one wrong
claimant, two claimants, combined tamper, resolver error, true orphan and valid
replay.

### F2 — P1: `cancelled -> cancelled` is still accepted as an exclusive Retry claim

**Code:**

- `app/api/routes/s10_full_apply.py:457-516`
- `app/api/routes/s10_full_apply.py:1364-1403`
- `tests/test_s10_full_apply_api.py:2407-2455`

`_s10_retry_claim_predecessor` still calls `_s10_cas_run_status` with
`from_statuses=("failed", "cancelled")` and `to_status="cancelled"`. On an
already-cancelled predecessor this is the exact no-op rejected by C6F §5.4.1.
SQLite reports one affected row for each no-op update, so rowcount is not an
exclusive ownership token.

Codex submitted and cancelled a fresh run, then invoked the real claim helper
twice in separate sessions. Actual result was:

`claim1=true, claim2=true, final status=cancelled`.

The simultaneous cancelled-Retry test asserts barrier rendezvous, response
codes and final one-successor state, but it never records or asserts claim
winner count. The unique successor-run constraint currently makes one request
lose later with 409, masking that both callers passed the alleged exclusive
claim. Final-row uniqueness is good backstop behavior, not proof that the CAS
claim contract was fixed.

**Required correction:** a failed predecessor may use the real
`failed -> cancelled` CAS. An initially cancelled predecessor must not use a
same-state update as ownership. Use a real state/version transition or treat
the atomic unique successor insertion as the ownership point and convert its
collision to stable 409. Tests must prove exactly one ownership winner/insert,
not only one final successor.
