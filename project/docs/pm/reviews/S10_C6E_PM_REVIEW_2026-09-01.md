## 3. Blocking findings

### F1 — P1: a wrong durable idempotency key is treated as a missing job and creates duplicate active work

**Code:**

- `app/api/routes/s10_full_apply.py:196-235`
- `app/api/routes/s10_full_apply.py:929-1004`
- `tests/test_s10_full_apply_api.py:1934-1970`

`_s10_find_durable_job` searches only for the expected exact idempotency key.
Therefore a durable job whose key was changed is invisible to the validator;
the replay path classifies it as missing and repairs by inserting another job.
The complete identity validator cannot reject the wrong key because it never
receives that row.

Codex used the real route, `JobService`, and fresh SQLite: normal Submit returned
202; only the stored job's `idempotency_key` was changed; identical replay then
returned **200 `reused=true`**. Final database truth contained **two queued Job
rows for the same run and deterministic generation**: one under the tampered
key and one under the canonical key. Expected result is 409/422 with one
unchanged row and no side effect.

The test named `test_c6e_wrong_identity_fails_closed_valid_control` says it
covers wrong idempotency key/job type/workspace/project/owner/generation, but it
actually mutates only generation, workspace and owner ID. This is a direct miss
of C6E §5.3 F2 and §5.4 item 7.

**Required correction:** discovery and validation must fail closed when any
durable S10 job already claims the run/generation/manifest identity with the
wrong key/type/workspace/owner. Legitimate missing-job repair is allowed only
after proving no conflicting row claims that identity. Add isolated mutations
for key, job type, owner type, manifest run/project identity and assert the
count over **all Job rows**, not only rows matching the canonical-key prefix.

### F2 — P1: Retry “claim” accepts `cancelled -> cancelled`; repeated Retry escapes as HTTP 500

**Code:**

- `app/api/routes/s10_full_apply.py:441-458`
- `app/api/routes/s10_full_apply.py:1247-1288`
- `app/services/s10_full_apply.py:670-716`

`_s10_retry_claim_predecessor` allows both `failed` and `cancelled` and writes
`cancelled`. On a cancelled predecessor this is a no-op update, yet SQLite
reports one affected row, so every caller can be told it won an exclusive CAS.
The route then tries to insert the same attempt-2 natural/idempotency identity.

Codex submitted and cancelled a normal run, called Retry once successfully,
then called Retry again on the same predecessor. Actual second response:
**500 Internal Server Error**, from the unique S10 run identity violation in
`retry_run`. Final durable counts happened to retain one successor because the
database backstop fired, but the API did not converge or return a stable
conflict and the claimed mutual exclusion is false.

**Required correction:** a no-op same-state update may not serve as an
exclusive claim. A repeated or simultaneous Retry on failed/cancelled
predecessors must deterministically leave one successor run/job and return a
truthful convergent result or stable 409 to losers, never raw/unhandled
`IntegrityError` or 500. Prove Retry-vs-Retry with true barriers on both source
states. No schema/migration is authorized unless a bounded implementation is
first disproved with reproduction evidence.

### F3 — P2: `worker_claim_vs_retry_barrier` is sequential, not a race test

**Code:**

- `tests/test_s10_full_apply_api.py:1978-2014`

Despite its name and docstring, the test transitions the queued job to running,
commits, and only then performs the Retry request. It creates no second thread,
`threading.Barrier`, Event rendezvous or concurrent request. Manager reports it
as one of two race tests, repeating the same evidence-quality error rejected in
C6D.

C6E made a deterministic worker-claim-versus-Retry barrier mandatory and made
missing barrier proof a binary exit failure. Replace this test with two real
participants: the worker must use the real revision/state CAS and Retry must
run concurrently. Evidence must include rendezvous count/tokens, both outcomes,
all run/job rows and the final active-lineage count. A sequential control may
remain separately but cannot be labeled concurrent.
