## 3. Blocking findings

### F1 — P1: truly concurrent identical replays create two queued jobs

**Code:**

- `app/api/routes/s10_full_apply.py:685-736`
- `app/persistence/models.py:678-686`
- `app/persistence/jobs.py:511-610`
- `tests/test_s10_full_apply_api.py:1596-1625`

The route performs a read-then-create sequence. Two requests can both observe
no job, reopen the same failed run, and enter `create_job`. The database index
includes nullable `input_generation`; both S10 calls omit it, and SQLite treats
NULL values as distinct in a unique index. Therefore the documented database
backstop does not serialize these inserts. The route also handles raw
`IntegrityError`, while the repository normally converts conflicts to the
stable job-domain exception.

Codex used the real route, real `JobService`, fresh isolated SQLite, two
`TestClient` instances, and a `threading.Barrier` immediately before the two
real `create_job` calls. Both responses were HTTP 200 with `reused=true`, but
the final database contained one pending run and **two different queued Job
rows with the same `s10_full_apply_job:<run-id>` idempotency key**.

This violates the central C6D acceptance condition and can let two workers
render/publish the same lineage. A loser-side compensation would also be wrong
if it changed the shared winning run to failed.

The test named `test_c6d_deterministic_concurrent_replays_one_run_job` is not
concurrent: lines 1612 and 1616 call replay A and then replay B serially. Its
docstring and Manager evidence therefore overstate what was tested.

**Required correction:** use a real database-enforced deterministic S10 job
generation/identity and explicitly converge the stable idempotency-conflict
path onto the winner without compensating the shared run. Prove one run, one
canonical job, one active work item, and truthful responses under actual
simultaneous repair. Do not weaken global durable-job semantics or add a
migration unless Codex separately authorizes that scope.

### F2 — P1: validator claims lifecycle validation but never performs it

**Code:**

- `app/api/routes/s10_full_apply.py:366-419`

The docstring explicitly promises to reject an active durable job paired with
a terminal run, but `_validate_replay_durable_job` ends after manifest equality
and never compares `stored["state"]` with `rec.status`.

Codex created a normal queued job, changed only its run to `cancelled`, and
sent an identical Submit replay. Actual result: HTTP 200, `reused=true`, public
status `cancelled`, durable job still `queued`. Expected: fail closed with no
mutation or duplicate work. A `completed + queued/running` contradiction must
likewise fail closed; only the explicitly valid lifecycle matrix may succeed.

### F3 — P1: manifest comparison is a whitelist, not complete immutable identity

**Code:**

- `app/api/routes/s10_full_apply.py:272-330`
- `app/workflow/job_service.py:408-414`

`JobService.create_job` durably injects `schema_version`, `managed_root`, and
`project_root`, but `_canonical_manifest_identity` intentionally excludes
`schema_version` and `project_root` and silently ignores extra keys. Codex
changed only stored `project_root` from the real MotionForge2D root to
`C:/TAMPERED/PROJECT_ROOT`; identical replay still returned HTTP 200
`reused=true`.

C6D required the complete immutable expected job manifest, not a selected
subset. The expected manifest must be canonicalized with the same server-side
defaults as durable creation, then compared exactly (including key set and
nested values). Missing, extra, malformed, or changed immutable fields must
fail closed.

**Model decision:** keep BAI DeepSeek for bounded C6E because its speed/cost is
substantially better than GLM, but make deterministic concurrency/lifecycle
probes binary manager gates. Codex independent review remains mandatory.
