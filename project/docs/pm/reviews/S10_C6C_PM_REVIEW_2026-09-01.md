## 3. Blocking findings

### F1 — P1: repaired replay exposes `failed` run + `queued` job, so Retry creates competing work

**Code:**

- `app/api/routes/s10_full_apply.py:228-278`
- `app/api/routes/s10_full_apply.py:511-574`
- `app/api/routes/s10_full_apply.py:761-871`
- `tests/test_s10_full_apply_api.py:1264-1289`

After the first Submit enqueue failure, C10 correctly compensates the run from
`pending` to `failed`. An identical replay then creates a durable job for that
same run, but `_s10_repair_missing_submit_job` never restores the run to a
claimable active status. The response is built from the unchanged ORM record,
so the route returns HTTP 200 with `status="failed"` while the job is `queued`.

Codex reproduced the sequence against the real route, real `JobService`, and
one fresh isolated SQLite database:

1. forced first enqueue failure -> HTTP 500, attempt 1 `failed`, zero jobs;
2. identical replay -> HTTP 200 `reused=true`, response/run `failed`, one
   `queued` job keyed `s10_full_apply_job:<run-1>`;
3. immediate `POST /full-apply/<run-1>/retry` -> HTTP 200, attempt 2 `pending`,
   second `queued` job keyed `s10_full_apply_job:<run-2>`.

There are now two claimable jobs for one logical lineage. Both can render or
publish, while the public response falsely presents the repaired run as failed.
The C10 test accepts any terminal/active job state and only checks the count for
the repaired run; it never asserts run/job coherence and never attempts Retry
while the repaired job is queued/running.

**Required correction:** repair must be one coherent state transition. Success
may expose exactly one active canonical run/job pair, never `failed + queued`.
Retry must reject or serialize against any active job for the predecessor
lineage. Concurrent replay, retry, and worker claim must still produce at most
one active canonical work item.

**Required tests:** immediate post-repair run/job state, Retry while repaired
job is queued/running, deterministic replay-vs-retry race, and worker-claim-
vs-retry race with exact run/job/attempt/publication/checkpoint counts.

### F2 — P1: replay proves only key existence and accepts a tampered immutable manifest

**Code:**

- `app/api/routes/s10_full_apply.py:196-225`
- `app/api/routes/s10_full_apply.py:511-520`

`_s10_find_durable_job` returns job state/key/manifest, but the caller uses only
`None` versus non-`None`. It does not validate job type, workspace/project
owner, run identity, or canonical immutable manifest/authority before returning
HTTP 200 `reused=true`.

Codex submitted a normal run, replaced that job's `input_manifest_json` with
`{"tampered":true}`, and replayed the identical request. The route still
returned HTTP 200, `created=false`, `reused=true`, `status=pending`. This is the
exact false-success case prohibited by the C6C acceptance contract. A later
worker/reconciler fence does not make an earlier successful API response true.

**Required correction:** canonicalize and compare the complete immutable
expected manifest and ownership identity before any replay success. Missing,
malformed, mismatched, cross-owner, wrong-job-type, or tampered durable jobs
must fail closed and must not create another job/run.

**Required tests:** mutate each material identity class (manifest authority,
run ID, owner, job type/key) and prove no 200/202/reused success and no new
durable side effect; retain a valid unchanged replay control.
