## 3. Blocking findings

### F1 — P1: Submit replay and Retry can expose an active run with no durable job

**Code:**

- `app/api/routes/s10_full_apply.py:346-410`
- `app/api/routes/s10_full_apply.py:612-684`

Both paths commit the run/attempt before creating the durable job. On enqueue
failure, Submit deliberately preserves the pending run and Retry only rolls
back a transaction that was already committed. Neither path compensates the
committed active row.

Codex reproduced both failures against the real route, real `JobService`, and
one isolated SQLite database:

1. Forced Submit `create_job` failure returned HTTP 500 but left one pending
   run with zero jobs. Replaying the identical request then returned HTTP 200,
   `created=false`, `reused=true`, still with `durable_job_count=0`.
2. After a real Submit and Cancel, forced Retry `create_job` failure returned
   HTTP 500 but left attempt 2 pending with natural key
   `s10_retry:<predecessor>:2` and `durable_job_count=0`.

This contradicts C6B's fail-closed lifecycle requirement and the T01C report's
claim that the failed retry successor does not exist. A pending run with no
claimable job can stall forever, and the Submit replay is a false HTTP success.

**Required correction:** exact T01C owner must make run+job creation atomic or
perform a durable CAS compensation to a coherent non-active state on every
post-commit validation/enqueue failure. A deduped Submit may return 200 only
after proving the matching durable job exists and is bound to the same
immutable manifest/authority. Retry may return success only after exactly one
matching successor job exists.

**Required tests:** forced Submit enqueue failure plus identical replay; forced
Retry authority/enqueue failure; exact DB assertions for run state, job count,
manifest/authority, predecessor truth, and idempotent recovery.

### F2 — P1: legacy/pre-existing-publication completion branch does not verify its CAS

**Code:** `app/workflow/s10_full_apply_jobs.py:769-792`

The normal publication path performs a conditional update and re-reads status
before publication/commit. The `has_completed` resume branch claims to use the
same CAS gate but executes the conditional update without inspecting rowcount
or live status. It then unconditionally writes a checkpoint containing
`"completed": true` and returns success.

If cancellation commits after `ctx.is_cancelled()` at line 774 but before the
conditional update, the update matches zero rows, the run remains cancelled,
and the handler still writes a completed checkpoint. The durable worker later
observes `cancelling` and drains the job, leaving contradictory durable truth.

**Required correction:** verify the completion CAS inside the same transaction.
If cancel wins, do not write a completed checkpoint or return handler success;
write only a non-completed checkpoint if appropriate and raise the existing
cancellation signal. Do not create or claim a new completed publication.

**Required tests:** a deterministic barrier around this exact branch with a
pre-existing completed publication, a nonterminal run/job, and cancellation
between the pre-check and completion CAS; also a no-cancel control proving the
legacy resume path still completes truthfully.

## 5. GLM 5.3 Flash versus DeepSeek V4 Flash

The C6B alias was not a controlled comparison. `comboBAI` currently contains
`BAI/glm-5.3-flash`, `BAI/deepseek-v4-flash-vision-exp`, and
`ocg/deepseek-v4-flash`. Read-only 9Router history for the C6B window records
984 GLM requests versus only 3 DeepSeek vision-exp requests, so C6B was
effectively a GLM run.

Official published coding/agent results favor GLM 5.3 Flash: Terminal-Bench
84.3 vs 82.7, NL2Repo 56.3 vs 54.2, DeepSWE 63.4 vs 54.4, Toolathlon 78.4 vs
70.3, and AutomationBench 48.8 vs 25.1. Both advertise a 1M context window.
Sources: [B.AI GLM 5.3 Flash model page](https://docs.b.ai/llmservice/models/glm-5-3-flash/)
and [DeepSeek official updates](https://api-docs.deepseek.com/updates/).

Local evidence also favors GLM for long, tool-heavy production work: it carried
the difficult C6B DAG through lifecycle, UI, build, and two vertical runs.
However, it used multiple continuations/context compression and missed F1/F2;
model choice does not replace an independent review.

**Decision:** use direct `BAI/glm-5.3-flash`, reasoning `max`, fallback OFF for
the next production correction and as the default complex coding worker for
the next opened sprint. Do not use `comboBAI`, because fallback makes model
attribution and quality/cost comparison ambiguous. Keep direct
`ocg/deepseek-v4-flash` as a cheaper bounded-worker/second-opinion option.

The local 9Router `cost` field recorded approximately 48.79 for GLM during the
C6B window, but this is router accounting metadata, not proof of a provider
charge. B.AI currently describes GLM 5.3 Flash as a limited 0-credit offer;
provider billing must be checked separately before treating the router estimate
as money paid.
